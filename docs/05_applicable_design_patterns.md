# 05. 결론 — 내 소프트웨어 개발에 적용 가능한 설계 패턴

> `docs/01~04, 06`에서 확인한 내용 중 "설계 아이디어로서" 다른 프로젝트에 옮겨 쓸 수 있는
> 부분만 추려 모은 요약입니다. DLSS5 자체는 독점 라이선스라 구조 참고만
> 가능합니다([[feedback_reference_not_reuse]]).

## 1. "파이프라인 끝단에 후처리 생성 단계를 붙인다"

**관찰**(`docs/03` §6): DLSS5는 기존 렌더링 로직을 전혀 안 건드리고, 완성된 프레임 +
G-buffer를 입력으로 받는 **별도의 후처리 생성 단계**로 설계됨. 기존 파이프라인을
리팩터링할 필요 없이 "끝에 하나 더 붙이는" 구조.

**적용**: 기존 시스템(예: 보고서 생성 파이프라인, 이미지 처리 체인)에 AI 기반 개선을
추가할 때, 기존 로직을 뜯어고치기보다 "최종 산출물 + 중간 산출물의 메타데이터(G-buffer에
해당하는 것)"를 입력받는 독립적인 후처리 단계로 붙이면 통합 리스크가 낮음.

## 2. 마스크/강도 조절 파라미터로 "생성의 개입 범위"를 통제

**관찰**(`docs/03` §2): 개발자가 마스크와 구조/톤 강도 값으로 DLSS5가 장면의 어느
부분을 얼마나 바꿀지 제어 가능.

**적용**: 생성형 AI를 파이프라인에 넣을 때 "전부 아니면 전무"가 아니라, 영향 범위를
공간적으로 마스킹하고 강도를 슬라이더로 조절 가능하게 설계하면 예측 불가능성을 국소화할
수 있음 — 특히 사용자 신뢰가 중요한 산출물(문서, 이미지)에 적용 가치 있음.

## 3. 핵심 모델은 닫아도 통합 API는 먼저 약속(원칙적으로는)

**관찰**(`docs/04`): Streamline/NVIGI 선례는 "모델 비공개 + API 헤더 공개"가 정상
패턴인데, DLSS5는 출시 시점에 API조차 미공개인 예외 사례로 관찰됨.

**적용(반면교사)**: 새 기능을 출시할 때 "기능 발표"와 "통합 가능한 API/SDK 공개" 사이에
공백이 생기면(DLSS5처럼) 서드파티가 비공식 방법(`docs/06`의 DLL 프록시 인젝션)으로 그
공백을 메우려는 생태계가 즉시 생겨남. 내가 뭔가를 공개할 때 이 시차를 의식적으로
관리할 가치가 있음 — 발표와 동시에 최소한의 공식 통합 경로를 열어두는 편이 비공식
생태계의 품질 편차(등급 c~d) 리스크를 줄임.

## 4. 화이트리스트 + 지문 DB 조합으로 점진적 롤아웃

**관찰**(`docs/06`): NVIDIA App의 `fingerprint.db` + `ApplicationStorage.json` 조합은
"이 기능을 어떤 대상에 얼마나 열지"를 서버측 마스터 데이터(지문 DB)와 로컬 설정
파일(오버라이드 가능한 JSON)로 분리.

**적용**: 신기능을 일부 대상에만 먼저 열고 싶을 때(베타, 단계적 롤아웃), 판정 로직을
서버측 참조 데이터로 관리하되 로컬에는 사람이 읽고 고칠 수 있는 오버라이드 파일을
남겨두면 디버깅/수동 예외 처리가 쉬워짐 — 단, 이건 동시에 `docs/06`처럼 우회의 표면적이
된다는 트레이드오프를 인지해야 함.
